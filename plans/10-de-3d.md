# Plan 10 — Dé 3D à l'écran

## L'idée

Quand on lance un dé, un vrai dé 3D traverse l'écran et se pose sur le résultat.
Le résultat chiffré n'apparaît qu'au moment où le dé se stabilise.

**Le code décide, le dé obéit.** `rollDie()` tire le résultat instantanément, comme
aujourd'hui. L'animation est une rediffusion : elle ne fait que montrer un dé qui
atterrit sur une face déjà connue. Aucun moteur physique.

C'est la technique standard (D&D Beyond, Foundry/Dice So Nice, dice-box-threejs),
sauf qu'on prend la variante « rotation vers un quaternion cible » plutôt que
« physique truquée » : pas de dépendance physique, durée contrôlée à la
milliseconde, annulation triviale.

## Contraintes posées

- Tous les jets de l'app sont animés.
- Le dé arrive d'un bord aléatoire de l'écran et vient au centre.
- **Pas d'assombrissement** : la page reste lisible derrière.
- Le résultat chiffré apparaît à la stabilisation, avec un petit pop.
- Skip au tap. Spam de clics = l'anim se relance sans lag.

## Le moteur

`utils/dice3d/` — trois morceaux purs, testables :

- `faceQuaternions.ts` — pour chaque type de dé, l'orientation qui met la face N
  face caméra. `setFromUnitVectors(normaleDeLaFace, +Z)`.
- `diceGeometry.ts` — géométries + atlas de textures. Une seule texture par type de
  dé (canvas avec N cases numérotées), UV calculées par face en projetant les
  sommets sur le plan de la face. Un seul draw call par dé.
- `rollAnimation.ts` — la trajectoire. Position : lerp bord → centre en ease-out.
  Rotation : `q(t) = spin(axeAléatoire, angleTotal × (1 − ease(t))) × qCible`.
  À t=1 le spin vaut l'identité, donc on tombe **exactement** sur la face voulue.

Ce qui est tiré au hasard à chaque lancer (purement cosmétique) : bord de départ,
axe de rotation, nombre de tours, durée. Deux fois le même résultat ne donnent
jamais la même animation.

## Perf

- Un seul renderer WebGL, créé au premier jet, jamais détruit.
- Géométries et textures en cache par type de dé.
- La boucle `requestAnimationFrame` ne tourne que pendant l'animation. Au repos :
  canvas caché, 0 % CPU.
- `import('three')` en lazy au premier jet → zéro impact sur le chargement.
- Nouveau clic pendant l'anim = on réinitialise `t` avec de nouveaux paramètres.
  Coût quasi nul.

## Le branchement

`composables/useDice3D.ts` expose `playDiceRoll(sides, values): Promise<void>`,
résolue quand le dé se pose. Chaque site de jet devient :

```ts
reveal(sides, [die], () => {
  // assignation du résultat affiché + addRoll()
})
```

`addRoll()` part **dans** le reveal : sinon le log affiche le résultat avant que le
dé ne se pose, ce qui vend la mèche. Les mutations d'état de jeu (coût en PM,
perte de PV) restent immédiates.

## Étapes

1. Moteur + overlay, branché sur la barre de dés (`DiceSandbox`). → vérif : les 7
   dés tombent sur la bonne face, spam de clics sans lag.
2. `ActionsView` : arme, action, carac, manœuvre, compétence, chance, deux armes.
   → vérif : chaque bouton anime, le résultat arrive après.
3. Le reste : `CombatView`, `AgonieModal`, repos, `HpGrowthModal`.
4. Réglage pour couper l'animation + respect de `prefers-reduced-motion`.

## Formes

d4/d6/d8/d12/d20 : géométries natives three.js. d10 : trapézoèdre pentagonal,
~20 lignes de sommets custom. d100 : deux d10 (dizaines + unités).
